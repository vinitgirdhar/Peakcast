# Research and technical assessment

Reviewed 2026-11-11. Primary sources below inform the architecture; they are not evidence that Wildcatter already implements the referenced systems.

1. **Existing exchange reference.** [Polymarket trading quickstart](https://docs.polymarket.com/trading/quickstart) distinguishes order placement, asynchronous on-chain settlement and position reads. Its current docs also distinguish protocol versions. Conclusion: adopt the separation of matching and settlement; do not copy stale SDK assumptions or claim an off-chain fill is final on-chain.
2. **Conditional tokens.** [Gnosis conditional-token contracts](https://github.com/gnosis/conditional-tokens-contracts) provide a reference implementation for outcome-based collateral/token accounting. Conclusion: evaluate reuse and licensing instead of inventing a token standard; integration and audits remain necessary.
3. **Resolution is disputable.** [UMA's prediction market integration](https://docs.uma.xyz/developers/optimistic-oracle-v3/prediction-market) and [Polymarket resolution](https://docs.polymarket.com/concepts/resolution) show oracle-driven resolution. Conclusion: gather evidence, propose, allow challenge, then finalize. Natural-language event contracts cannot honestly promise zero ambiguity or unconditional 60-second finality.
4. **Regulation is a product constraint.** [CFTC explanation of prediction markets](https://www.cftc.gov/LearnandProtect/PredictionMarkets) describes regulated event contracts and exchange obligations. This is a U.S. reference only, not a global legal opinion or permission to operate. Conclusion: launch jurisdiction and entity/partner decisions precede real-money enablement; IP geolocation alone is not authorization.
5. **Desktop delivery.** [Electron security guidance](https://www.electronjs.org/docs/latest/tutorial/security) recommends isolation, sandboxing, navigation restrictions and careful permission handling. [Tauri prerequisites](https://tauri.app/start/prerequisites/) require native toolchains. Decision: Electron for this Windows milestone, reusing the API/UI without a separate Rust/native integration. Ship a local demo server, not filesystem/Node access in the renderer.
6. **Installable mobile web.** [MDN PWA installation guidance](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable) covers manifest, platform behavior and secure-context requirements. Decision: PWA plus responsive UI; do not describe it as a native mobile binary. API requests remain network-only.
7. **API validation.** [Fastify validation/serialization](https://fastify.dev/docs/latest/Reference/Validation-and-Serialization/) and [Swagger integration](https://github.com/fastify/fastify-swagger) support route schemas and generated documentation. Decision: versioned Fastify routes with boundary validation and an OpenAPI document derived from those routes.
8. **AI interface.** [OpenAI structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs) and [Responses create reference](https://developers.openai.com/api/reference/resources/responses/methods/create) support constrained JSON output. Decision: use the official SDK, configurable server-side model, strict schema and local validation. Schema validity is not factual correctness; market drafts still need evidence and review. No live model call is necessary to run the demo.
9. **Local persistence.** [Node SQLite documentation](https://nodejs.org/api/sqlite.html) describes `DatabaseSync` and prepared statements. Decision: transactional, single-process demo storage; migrate to a production ledger/database before horizontal scaling.

## Why the entire RFP is not one implementation milestone

The document is an RFP, not an executable specification: chain/collateral, exact order semantics, market invalidation, fee policy, dispute arbitration, KYC vendors, country policy and funding partners are unspecified. Its absolute claims (guaranteed liquidity, zero ambiguity, instant finality, fixed gas cost) depend on economics, data quality, finality and external operators. The implementation plan preserves the requested end state while replacing those claims with testable acceptance criteria.

## Initial interface direction (superseded by docs/DESIGN.md)

An analytical forecasting workspace: paper white `#f6f8fb`, navy ink `#182333`, cobalt action `#315cf5`, teal YES `#087f70`, berry NO `#b33d62`, slate secondary `#66748b`. A compact left navigation rail, broad market canvas and contextual detail/trade area. System sans typography with tabular probabilities and balances; no decorative live tickers or invented activity. Category icons and probability bars carry the visual identity. Left-aligned text, keyboard focus, mobile bottom navigation and visible demo/data-source labels.

The main visual emphasis is the forecast itself: a large probability plus a clearly legible YES/NO bar, with the question and resolution source adjacent. Avoid a generic promotional landing page: the first screen is a useful market explorer.
